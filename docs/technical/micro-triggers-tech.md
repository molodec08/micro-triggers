# Бриф: "Микро-триггеры внимания" — техническая часть

См. также: [бизнес-часть](../business/micro-triggers-brief.md).

Разработчик: React/TS/Vue на фронте, Node.js + PostgreSQL (Sequelize) на бэке.
Иностранная карта есть — платёжных ограничений нет.

## Технический стек
- Шаблон: **React Router app** (актуальная замена Remix-шаблона в Shopify CLI),
  НЕ extension-only — нужен бэкенд для настроек и Billing API
- Admin UI: Polaris — простые тумблеры вкл/выкл на каждый триггер, live-превью
- Storefront: Theme App Extension (Liquid + JS), вся логика триггеров — чистый
  клиентский JS, максимально лёгкий бандл
- БД: Postgres (в шаблоне по умолчанию SQLite — заменить провайдера в Prisma
  schema.prisma). Схема: shop → какие триггеры включены, тексты, задержки, файл звука
- Учитывать при тестировании: блокировщики рекламы/приватности в браузере иногда
  режут audio/visibility API

## Реализация триггеров (MVP v1)
1. **Мигающая вкладка браузера** при уходе с вкладки, если в корзине есть товар
   (`visibilitychange` → смена `document.title` и favicon, возврат при фокусе)
2. **Минималистичный exit-intent попап** (отслеживание движения мыши к верхней
   границе окна)
3. **Звуковой сигнал** при добавлении в корзину / на checkout (Web Audio API)

## Исправлено, 2026-07-20: тип `s-app-nav`

`@shopify/polaris-types@1.0.7` (актуальная опубликованная версия — апгрейд не
помогает) не объявляет `<s-app-nav>`, хотя это реальный, поддерживаемый рантаймом
компонент ("App nav web component", см. shopify.dev/docs/apps/design/navigation).
Остальные `s-*` теги регистрируются пакетом через
`declare module "react" { namespace JSX { interface IntrinsicElements {...} } }`
— `s-app-nav` там просто пропущен.

Временный патч в `env.d.ts`: локальный augmentation того же модуля `react` для
`s-app-nav`. Ключевой нюанс — `env.d.ts` должен быть модулем (иметь `import`),
иначе `declare module "react"` не мержится с существующими типами `@types/react`
и вместо этого либо не резолвится, либо ломает остальные экспорты `react`
(`useState` и т.д.). Добавлен `import type { DetailedHTMLProps, HTMLAttributes }
from "react"` в начало файла — после этого `npm run typecheck` проходит чисто.

Удалить этот патч, когда в `@shopify/polaris-types` появится нативное
объявление `s-app-nav`.

## Шаг 3 (Storefront: реализация трёх триггеров) — выполнено, 2026-07-20

**Theme App Extension** — `extensions/micro-triggers-storefront/`, сгенерирован
через `shopify app generate extension --template=theme_app_extension`. Демо-файлы
шаблона (`star_rating.liquid`, `stars.liquid`, `thumbs-up.png`) удалены.

Один **app embed block** (`blocks/app_embed.liquid`, `target = "body"`) —
мерчант включает его один раз в редакторе темы; блок подключает единственный
JS-файл `assets/micro-triggers.js` (без сборки, без зависимостей — весь код
трёх триггеров в одном файле на чистом ES5, чтобы бандл оставался лёгким).

**Передача настроек на сторфронт: App Proxy**, а не metafields — единственный
источник правды для настроек остаётся Postgres (см. шаг 2), без риска
рассинхронизации с дублирующим хранилищем.
- `shopify.app.toml`: добавлен `[app_proxy]` (`prefix = "apps"`,
  `subpath = "micro-triggers"`) и обязательный для него access scope
  `write_app_proxy` (ранее было `scopes = ""` — пересмотрено на шаге 3, так как
  App Proxy — не Admin GraphQL API, но тоже требует явного scope).
- `app/routes/proxy.settings.tsx` — публичный (без Admin-сессии) route,
  `authenticate.public.appProxy(request)` определяет `shop` по запросу,
  дальше читает три Prisma-модели и отдаёт единый JSON.

**Логика триггеров в `micro-triggers.js`**
1. **Мигающая вкладка** — `visibilitychange`; при уходе со страницы с
   непустой корзиной (`GET /cart.js`) чередует `document.title` с текстом
   настройки раз в секунду; возвращает исходный заголовок при фокусе.
2. **Exit-intent попап** — слушает `mouseleave` на `document`, срабатывает
   только когда курсор уходит через верхнюю границу (`clientY <= 20`) и в
   корзине есть товар; рисует минимальный оверлей (текст + промокод +
   кнопка закрытия) без сторонних библиотек.
3. **Звук** — Web Audio API (`AudioContext`, короткий синус-бип), без
   аудиофайлов. Слушает `submit` форм с `action` на `/cart/add`
   (добавление в корзину) и клики по ссылкам на `/checkout`, каждый — под
   своим флагом (`playOnAddCart`/`playOnCheckout`) из настроек.

**Учтено при написании**: весь фетч настроек и `/cart.js` обёрнут в
`try/catch`/`.catch()` — если блокировщик приватности режет `fetch`/`AudioContext`,
триггеры просто не активируются, без ошибок в консоли витрины.

**Не проверено вручную** (нужно сделать в шаге 5, QA): реальная работа на
dev store — прогонялась только статическая проверка (`npm run lint`,
`npm run typecheck`), реального рендеринга в браузере на теме Dawn/Horizon
ещё не было.

## Диагностика, 2026-07-20: редирект на список приложений вместо /app

**Симптом**: переход на `.../apps/simple-app-121/app` в Shopify admin сразу
редиректил на `.../settings/apps?tab=installed` (список установленных
приложений), без видимой ошибки — в логе `shopify app dev` была только строка
`Authenticating admin request`, без продолжения и без стектрейса.

**Причина**: только что добавленный `billing.check()` в loader'е
`app/routes/app.tsx`. План Shopify App Pricing ($9/мес) ещё **не создан** в
Partner Dashboard (это отдельный ручной шаг — см. раздел "Шаг 4" выше).
Без существующего плана `billing.check()` бросает необработанную ошибку;
необработанная ошибка в loader'е embedded-приложения приводит к тому, что
Shopify admin трактует приложение как неработающее и откатывается на список
установленных приложений — без явного сообщения об ошибке на экране.

**Промежуточное решение (было)**: `billing.check()` и связанный с ним редирект
на pricing_plans временно закомментированы в `app/routes/app.tsx`.
Подтверждено: после отключения `/app` открывается нормально.

**Финальное решение (текущее состояние кода)**: `billing.check()` возвращён и
обёрнут в `try/catch` с политикой **fail-open** — если проверка биллинга
бросает ошибку (пока нет плана в Partner Dashboard), доступ к `/app`
разрешается, ошибка только логируется через `console.error`. Редирект на
pricing_plans срабатывает только если `billing.check()` успешно отработал и
явно вернул `hasActivePayment: false`.

Это осознанный компромисс: строгий gate (падать/блокировать при ошибке
`billing.check()`) недопустим сейчас, потому что редиректил бы на
несуществующую страницу плана и ронял бы всё приложение — именно это и
произошло в описанном выше симптоме. Fail-open даёт корректное поведение в
обоих состояниях:
- **план не создан** (сейчас) — ошибка, доступ разрешён, приложение работает;
- **план создан, но нет подписки** — `billing.check()` успешен,
  `hasActivePayment: false`, происходит редирект на pricing_plans как и
  задумано.

**Оставшийся ручной шаг**: создать план Shopify App Pricing ($9/мес,
7-дневный trial, без капов) в форме сабмита приложения на
partners.shopify.com. Код меняться не должен — gate заработает штатно сам
по себе, как только план появится.

### Уточнение, 2026-07-20: `billing.check()` бросает `Response`, не `Error`

При живом прогоне (`shopify app dev`) пойманное в `catch` значение оказалось не
обычной ошибкой, а объектом `Response` со статусом **200** и телом HTML
(с CSP-заголовками `frame-ancestors` под iframe embedded-приложения) — то есть
похоже на служебную страницу SDK, а не на код ошибки в привычном смысле.

Гипотеза "это штатный `throw Response`-редирект, который нужно пробрасывать
дальше (`throw error`), а не глотать" была проверена и **отклонена на
практике**: после `throw error` вместо `console.error` страница снова начала
редиректить на список приложений — то же самое некорректное поведение, что и
до всякой обработки ошибок. Значит текущий swallow-подход (полностью глотать
и логировать, без re-throw) — не временный костыль, а единственно рабочее
поведение из проверенных на данный момент.

**Открытый вопрос** (не выяснено, пока план не создан в Partner Dashboard):
почему `billing.check()` вообще бросает `Response`, а не просто резолвит
`hasActivePayment: false` или бросает обычную ошибку. Возможно, это связано с
отсутствием сессии/токена в конкретный момент, а не с отсутствием плана как
таковым — стоит перепроверить это место после того, как план появится: если
ошибка исчезнет сама, значит дело было в конфигурации биллинга; если
`Response`-throw повторится и тогда, потребуется более глубокое исследование
(возможно, отдельный вопрос в Shopify community/поддержку).

## Исправлено, 2026-07-20: iframe-превью не грузился

**Симптом**: на странице приложения в секции превью — "Сайт
simple-dev-2s9mhugw.myshopify.com не позволяет установить соединение."

**Причина**: архитектурная ошибка на шаге 4 — витрины Shopify по умолчанию
отдают заголовки (`X-Frame-Options`/CSP `frame-ancestors`), запрещающие
встраивание в `<iframe>` с чужого origin. Admin UI приложения рендерится в
своём iframe внутри `admin.shopify.com`, что для самой витрины — чужой домен;
это защита от clickjacking на уровне платформы, не зависит от настроек
конкретного магазина и не обходится кодом приложения. Идея "живой iframe" из
шага 4 была нежизнеспособна с самого начала.

**Исправление**: `<iframe>` заменён на `<s-link target="_blank">`, открывающую
магазин в новой вкладке. Полноценного inline-превью триггеров в текущем виде
нет — компромисс, принятый вместо решения этой задачи (например, скриншот
через отдельный сервис) в рамках MVP.

## Диагностика, 2026-07-20: триггеры не срабатывают на витрине

**Симптом**: все три триггера включены в Admin UI, товар добавлен в корзину,
переход на другую вкладку — ни звука, ни изменения заголовка, ни попапа.

**Причина**: app embed блок "Micro-triggers" (шаг 3) ещё не был включён на
самом dev store через редактор темы. Это ручное действие, которое нельзя
выполнить через CLI/код — Theme App Extension по архитектуре Shopify требует
явного согласия мерчанта на встраивание в тему через UI редактора. Без этого
шага `assets/micro-triggers.js` физически не подключается ни к одной странице
витрины, поэтому все обработчики событий (`visibilitychange`, `mouseleave`,
`submit`) просто отсутствуют в DOM.

**Что нужно сделать вручную** (см. также раздел "Шаг 4" выше про то же
ограничение для dev store):
1. `npx shopify app dev` (если ещё не запущен) — подключит расширение к
   dev store.
2. В Shopify admin: **Online Store → Themes → Customize** (редактор темы) на
   `simple-dev-2s9mhugw.myshopify.com`.
3. В левой панели редактора — вкладка **App embeds** (иконка пазла обычно
   внизу списка блоков).
4. Найти "Micro-triggers" и включить тумблер.
5. Сохранить (**Save** в редакторе темы).
6. Добавить любой товар в корзину на витрине и только после этого проверять
   триггеры (переключение вкладки, движение курсора к верхней границе,
   добавление в корзину).

Пока этот шаг не сделан, отсутствие эффекта от триггеров — ожидаемое
поведение, не баг в коде.

## Добавлено, 2026-07-20: подсказка про app embed прямо на странице приложения

По итогам предыдущей диагностики стало ясно, что инструкцию про включение app
embed блока нужно показывать не только в docs, но и мерчанту прямо в Admin UI
— иначе неактивные триггеры выглядят как баг.

`app/routes/app._index.tsx`: добавлена секция "Enable on your theme" со
ссылкой-**deep link** в редактор темы, которая сразу открывает вкладку
"App embeds" с предвыбранным блоком "Micro-triggers" (мерчанту остаётся только
включить тумблер и нажать Save, не искать блок вручную):

```
https://{shop}/admin/themes/current/editor?context=apps&template=index&activateAppId={api_key}/app_embed
```

## Шаг 5 (QA) — прод-хостинг на Railway, 2026-07-21

**Выбор платформы**: Railway вместо Vercel+Supabase — по стоимости. Vercel
Hobby (бесплатный) по ToS запрещён для коммерческих проектов (приложение

вышла бы ~$45/мес против Railway Hobby $5/мес (app + Postgres в одном
проекте, включённый usage-кредит $5/мес).

**Домен**: `https://micro-triggers-production.up.railway.app`. Прописан в
`shopify.app.toml` (`application_url`, `[app_proxy].url`,
`[auth].redirect_urls`) вместо прежней заглушки `https://example.com`.
Существующий `Dockerfile`/`.dockerignore` из шаблона Shopify CLI использован
как есть — сборка через `docker build` проверена локально перед деплоем,
прошла чисто.

**Проблемы при первом деплое и их решение** (по порядку, как всплывали):

1. **`DATABASE_URL` не найден** — переменная в Railway была задана как
   reference `${{Postgres.DATABASE_URL}}`, но Postgres-сервис физически
   находился в другом Railway-проекте (`handsome-connection`), а приложение —
   в `pleasant-youthfulness`. **Reference между сервисами работает только
   внутри одного проекта** — межпроектные ссылки резолвятся в пустую строку
   без явной ошибки о причине. Решение: создан новый Postgres-сервис прямо в
   проекте с приложением.
2. **`DATABASE_URL` резолвился в `<empty string>`** даже после создания
   Postgres в том же проекте — сама переменная-reference в сервисе
   приложения была утеряна/не пересоздана автоматически при смене источника.
   Решение: пересоздана через встроенную подсказку Railway "Trying to connect
   a database? Add Variable" (выбор сервиса из списка, не ручной ввод
   `${{...}}"`, чтобы исключить опечатку).
3. **`Detected an empty appUrl configuration`** (ошибка из
   `@shopify/shopify-app-react-router`, `app/shopify.server.ts:15` —
   `appUrl: process.env.SHOPIFY_APP_URL || ""`) — эта переменная не входит в
   стандартный набор (`DATABASE_URL`/`SCOPES`/`SHOPIFY_API_KEY`/
   `SHOPIFY_API_SECRET`), нужна отдельно и не генерируется автоматически.
   Решение: добавлена `SHOPIFY_APP_URL` = тот же домен, что и
   `application_url` в `shopify.app.toml`.
4. **HTTP 502 снаружи домена**, при этом контейнер в логах выглядел живым
   (`[react-router-serve] http://localhost:8080`) — рассинхрон портов:
   Railway **Networking** проксировал домен на порт **5000** (видимо,
   остаток от более раннего автоопределения), а `react-router-serve` слушал
   **8080** (порт из `process.env.PORT`, который Railway передаёт в
   контейнер и который может отличаться между деплоями, если не закреплён
   явно). Решение: зафиксирована переменная `PORT=8080` в Variables сервиса
   **и** вручную выставлен тот же порт 5000→8080 в Settings → Networking →
   Public Networking, чтобы оба значения гарантированно совпадали при любом
   будущем деплое.

**Результат**: `curl https://micro-triggers-production.up.railway.app/` →
`200 OK`. `npx shopify app deploy` выполнен, новая версия конфигурации
(`micro-triggers-2`) опубликована — `redirect_urls` и App Proxy URL на
стороне Shopify синхронизированы с реальным доменом.

**Старый Postgres в `handsome-connection`** (другой Railway-проект) остался
неиспользуемым — не удалён, стоит проверить и удалить отдельно, если там нет
нужных данных, чтобы не платить за лишний ресурс.

**Диагностика при настройке `vite.config.ts`** (три связанные проблемы,
все всплыли на этапе первой пробной сборки, ни одна не была очевидна из
документации Vite/Rollup):
1. **Циклическая зависимость entry-чанков** — исходная версия `shared.ts`
   была экспортирована прямо из `core.ts` (не из отдельного файла). Rollup
   в такой конфигурации инлайнит общий код в `core.js` и заставляет каждый
   триггер-чанк доимпортировать недостающее обратно из `core.js` — то есть
   загрузка любого одного триггера тянула за собой весь диспетчер
   (включая логику загрузки *остальных* триггеров). Устранено вынесением
   `shared.ts` в файл, который не импортируется `core.ts` кружным путём —
   `core.ts` и все триггеры импортируют `shared.ts` независимо друг от
   друга, `manualChunks` в `vite.config.ts` дополнительно форсирует его в
   собственный чанк.
2. **Пустые chunk-заглушки** — при явном перечислении всех триггеров в
   `rollupOptions.input` (чтобы получить предсказуемые имена файлов без
   хэша) Rollup создавал файлы вида `blinking-tab.js` размером 0 байт, а
   реальный код уезжал в отдельный `shared-blinking-tab.js`, от которого
   `core.js` зависел напрямую, минуя пустышку. Причина — Rollup сам
   резолвит динамический `import()` до фактического чанка с кодом и не
   обязан привязывать его к заявленному entry-имени, если модуль не
   экспортирует ничего "снаружи" видимого самому entry. Исправлено отказом
   от перечисления триггеров как entry points: единственный entry —
   `core.ts`, Vite сам генерирует по одному чанку на каждый динамически
   импортированный модуль (`chunkFileNames: "[name]-[hash].js"` — хэш в
   имени неизбежен при таком подходе, но `core.js` сам содержит правильные
   ссылки на актуальные хэши после каждой сборки, так что это не проблема).
3. **Абсолютные пути в modulepreload-хелпере** — Vite по умолчанию вставляет
   в бандл `__vitePreload`-хелпер, который строит `href` для
   `<link rel=modulepreload>` как `"/" + filename` (абсолютный путь от
   корня домена). Для Theme App Extension это некорректно: ассеты
   раздаются с per-магазинного CDN-пути через Liquid `asset_url`, а не с
   корня сайта — такой `<link>` указывал бы в никуда (лишний, тихий 404,
   не ломающий сам код-сплиттинг, поскольку фактические `import()` вызовы
   резолвятся браузером относительно URL `core.js` нативно и корректно, но
   всё равно нежелательный шум). Исправлено через
   `build.experimental.renderBuiltUrl` → `{ relative: true }` в
   `vite.config.ts`.

**Ассеты в git**: собранные `assets/*.js` (`core.js` + по одному файлу на
триггер) по-прежнему коммитятся в репозиторий, как раньше коммитился
единственный `micro-triggers.js` — в проекте нет CI/CD, `shopify app
deploy`/`dev` не запускают сборку extension сами. Вместо этого:
`package.json` в корне получил `build:extension`
(`npm run build --workspace=micro-triggers-storefront`), подключённый в
`build` (перед `react-router build`) и в `predev` (перед `shopify app
dev`) — так что обычный локальный воркфлоу пересобирает extension
автоматически, но **если кто-то деплоит без прогона этих npm-скриптов
(например, вручную через `shopify app deploy` напрямую), нужно сначала
вручную прогнать `npm run build:extension`**, иначе задеплоится
устаревший бандл.

**Watch-режим для `npm run dev`, 2026-09-12 (в тот же день, отдельным
заходом)**: `predev` даёт только разовую сборку при старте — правки в
`src/*.ts` после этого не подхватывались бы сами, пока `shopify app dev`

`shopify app dev` — интерактивный процесс со своим терминальным UI
(QR-код, лог, перехват клавиш), поэтому оставлен как есть, а extension

Проверено вручную: запуск `npm run dev:extension` в фоне, правка файла в

## Шаг 8: перенос build-тулинга из extensions/ в app/, 2026-09-12 (тот же день)

**Симптом**: первый же `npm run dev` (→ `shopify app dev`) после шага 7 упал:

```
❌ Error
└  Only assets, blocks, snippets, locales directories are allowed
```

**Причина**: Shopify CLI валидирует структуру каждой theme app extension
директории и разрешает там строго `assets/`, `blocks/`, `snippets/`,
`locales/` (плюс `shopify.extension.toml`) — ничего больше. Шаг 7 положил
`src/`, `package.json`, `tsconfig.json` и `vite.config.ts` прямо в
`extensions/micro-triggers-storefront/`, рядом с `assets/`, что CLI не
ожидал. До этого исправления `npm run build:extension` (обычная
одноразовая сборка) отрабатывал без проблем — ошибку показывал только сам
`shopify app dev`, который дополнительно валидирует структуру директории
перед тем, как её отдать.

**Исправление**: build-тулинг для storefront-скрипта перенесён из
`extensions/micro-triggers-storefront/` в `app/storefront-src/`
(`src/`, `package.json`, `tsconfig.json`, `vite.config.ts`) — выбор в
пользу `app/` сделан явно (альтернативой было вынести это в отдельный
top-level пакет вроде `packages/`), чтобы не плодить новых top-level
директорий в репозитории. `app/` для React Router-приложения используется
как source root только через `app/routes/` (`flatRoutes()` в
`app/routes.ts`), так что соседняя `app/storefront-src/` не подхватывается
роутингом — подтверждено: `npm run build` после переноса продолжает
собирать ровно тот же набор роутов, что и раньше.

Теперь в `extensions/micro-triggers-storefront/` остаются только
`assets/` (собранный вывод), `blocks/`, `locales/`, `shopify.extension.toml`
— то есть ровно тот набор, который был до шага 7 и который ожидает CLI.

**Что изменилось технически**:
- `pnpm-workspace.yaml` и корневой `package.json` (`workspaces`): путь
  `extensions/*` дополнен отдельной записью `app/storefront-src` (имя
  npm-пакета осталось `micro-triggers-storefront` — скрипты
  `build:extension`/`dev:extension`/`predev` в корневом `package.json`
  резолвят workspace по имени пакета, не по пути, поэтому их менять не
  пришлось).
- `app/storefront-src/vite.config.ts`: `build.outDir` теперь не
  относительный `"assets"` (это было верно, когда конфиг лежал рядом с
  `assets/`), а абсолютный путь, вычисленный через
  `resolve(dirname(fileURLToPath(import.meta.url)), "../../extensions/micro-triggers-storefront/assets")`
  — конфиг пишет собранные файлы через директорию наружу, в старое место.
  `__dirname` использовать нельзя напрямую: пакет `"type": "module"`,
  значит `vite.config.ts` может исполняться как ESM, где `__dirname`
  не определён — отсюда `fileURLToPath(import.meta.url)`.

**Проверено**: `npm install` (workspace резолвится в новый путь,
подтверждено `npm ls --workspaces`), `npm run build:extension` (пишет в
прежнее `assets/`, те же имена/хэши файлов, что и до переноса — код не
менялся), `npx tsc --noEmit --project app/storefront-src/tsconfig.json`,
`npm run typecheck` и `npm run lint` в корне (оба чисто, включая
`app/storefront-src/`), `npm run build` (полная сборка, список роутов в
`build/client/assets/` не изменился — `app/storefront-src/` в него не
попал). Живой `shopify app dev` в этой сессии не перезапускался — сама
ошибка диагностирована по структуре, которую CLI документирует явно,
но реальный успешный старт `shopify app dev` после переноса стоит
подтвердить отдельно.

## Шаг 9: диагностика "dev режим перестал работать", 2026-09-12 (тот же день)

После шага 8 пользователь перезапустил `npm run dev` и столкнулся с
цепочкой из трёх раздельных симптомов подряд — каждый со своей причиной,
не связанной с кодом самого приложения.

### 9.1 Горячая клавиша `p` (открыть preview) не реагирует через `concurrently`

`npm run dev` теперь запускает `shopify app dev` не напрямую, а через
`concurrently` (см. предыдущую запись про watch-режим) — добавлен `-i
--default-input-target=shopify`, чтобы stdin форвардился в дочерний процесс.
**Не проверено до конца** — есть теоретический риск, что `shopify app dev`
использует Ink/React для интерактивного UI, которому в общем случае нужен
настоящий TTY для посимвольного ввода без Enter; через `concurrently`
stdin — это pipe, не TTY. Если горячие клавиши всё ещё не реагируют,
запасной вариант — не использовать `concurrently` для интерактивной
работы: `shopify app dev` в одном терминале напрямую, `npm run
dev:extension` в другом.

### 9.2 Зависшие дубликаты процессов после нескольких перезапусков

Несколько раз подряд остановленный и заново запущенный `npm run dev`
оставлял зависшие процессы вместо полного завершения (Windows-специфика
обрыва процесса из терминала) — обнаружено **два одновременных**
`@react-router/dev/bin.js dev` процесса и отдельно зависший процесс на
порту GraphiQL (`3457`, `EADDRINUSE`). Старый процесс отвечал на запросы
устаревшим кодом, из-за чего новые роуты (`/app/styling`) не находились
(404) даже после того, как актуальный процесс был явно запущен и вывел
"✅ Ready".

**Диагностика**: `Get-CimInstance Win32_Process | Where-Object {
$_.CommandLine -match "react-router.*dev|shopify.*app dev" }` — если
показывает больше одного дерева процессов с разным `CreationDate`, старые
зависли и их нужно `Stop-Process -Force`. Общий рецепт: если после
перезапуска `npm run dev` что-то ведёт себя как "старая версия" несмотря
на подтверждённый в коде фикс — первым делом проверить, нет ли
дублирующегося процесса на тех же портах, а не искать причину в коде.

### 9.3 Триггеры не работают на витрине — app embed нужно включать в dev-теме, не в основной теме магазина

Это главный, неочевидный практический вывод сессии — **зафиксировать на
будущее**.

**Симптом**: приложение в admin работает, все триггеры включены в
настройках, но на обычном URL магазина (`https://{shop}.myshopify.com/`,
без параметров) ничего не происходит — ни popup, ни бары, ни звук.
`core.js` вообще не встречается среди `<script>` тегов страницы (проверено
через `document.querySelectorAll('script[src]')` в консоли, а не через
Network-таб — см. ограничение ниже).

**Причина**: пока `shopify app dev` запущен, он создаёт (или переиспользует
уже созданную) **отдельную служебную тему** в Shopify admin с именем вида
`App Ext. Host (<hostname>)`, ролью **`development`** — не путать с
основной темой магазина ("Savor" в этом проекте) и её ролью `main`/live.
Обычный URL магазина без `preview_theme_id` в параметрах отдаёт именно эту
dev-тему для той сессии/аккаунта, что залогинена в CLI — а не
опубликованную. Это подтверждается прямо в рантайме:
```js
window.Shopify.theme // { id: 167406108761, name: "App Ext. Host (...)", role: "development" }
```
Каждая из тем — и основная ("Savor"), и служебная dev-тема — имеет
**свой собственный, независимый** список App embeds с собственным
состоянием тумблера "Micro-triggers". Включение блока в редакторе основной
темы ("Savor") не включает его в dev-теме, и наоборот — это два разных
объекта в Shopify, оба видны как отдельные пункты в списке тем
(`/admin/themes`).

**Исправление**: в Shopify admin → **Online Store → Themes**, найти тему с
ролью **Development** (не ту, что помечена Active/Published) →
**Customize** → вкладка **App embeds** (иконка пазла) → включить тумблер
"Micro-triggers" → **Save**. Deep-link для этого (уже реализованный в
`app/routes/app._index.tsx`, секция "Enable on your theme") открывает
`themes/current/editor` — `current` резолвится в **активную** тему
пользователя в браузере на момент клика, что на практике почти всегда
совпадает с нужной dev-темой, пока `shopify app dev` запущен и работает
для этого пользователя, но не гарантированно — если сомневаетесь, что
включили в правильной теме, проверьте `window.Shopify.theme.role` в
консоли на живой странице магазина, как показано выше, и откройте именно
ту тему по её реальному `id` в списке `/admin/themes`.

**Не полагаться на Network-таб/`read_network_requests` MCP-инструмент
браузера для проверки, грузится ли `core.js`** внутри редактора темы —
theme preview рендерится в кросс-доменном `<iframe>`, и наблюдалось, что
инструмент трекинга сети не видит запросы из вложенного фрейма (постоянно
сообщал "tracking starts now" и ноль результатов даже после множества
перезагрузок). Надёжная проверка — выполнить в консоли самой страницы
(не редактора темы, а прямого URL магазина):
```js
Array.from(document.querySelectorAll('script[src]'))
  .map(s => s.src)
  .filter(s => s.includes('core.js'))
```
Пустой результат — `core.js` не подключён (app embed выключен в
обслуживающей эту сессию теме); непустой (путь вида
`https://cdn.shopify.com/extensions/<uid>/dev-<hash>/assets/core.js`) —
extension подключён и должен работать.
